Chapter 1

The problem

Week 6 of the thesis…
SamWhich of these files actually worked last Tuesday?!
Suddenly…
SnapHi! I'm Snap. I'm basically what Git does: I take snapshots of your whole project folder, whenever you tell me to.
One folder, full history
SnapEach snapshot is a commit. It remembers what changed, who did it, when, and a short message saying why.

What you get: go back to any earlier version, see exactly what changed between two versions, try risky ideas without breaking working code, and share code with teammates (or your supervisor) without emailing zip files. Git runs locally on your computer. GitHub and GitLab are websites that host a copy of your Git project online; you'll meet them in Chapter 8.

Chapter 2

Setup (once per computer)

Is Git installed?
SnapOpen a terminal and ask me my version.
$ git --version
git version 2.4x.x

Not found? macOS: run xcode-select --install (or brew install git). Ubuntu/Debian: sudo apt install git. Windows: install “Git for Windows” from git-scm.com.

Tell Git who you are
SnapI sign every snapshot with your name and email. Use the same email as your GitHub account.
$ git config --global user.name "Ada Student"
$ git config --global user.email "ada@example.com"
$ git config --global init.defaultBranch main
# check it worked
$ git config --list

--global means “for every project on this computer”, so you only do this once.

Chapter 3

The three places your files live

The most important page in this issue
SnapThink of a photo shoot. First you choose who stands on the stage (git add). Then you press the button (git commit).

Working directory

Your normal project folder. You edit files here.

Staging area

The list of changes that will go into the next snapshot.

Repository

All saved snapshots, kept in the hidden .git folder.

SamWhy not just snapshot everything at once?
SnapSay you fixed a bug and started a new feature. Two separate photos, “Fix bug” and “Start feature”, tell a much clearer story later.
Chapter 4

Your first commit

Step 1 · Start tracking a folder 
$ mkdir my-project
$ cd my-project
$ git init
Initialized empty Git repository
in /Users/ada/my-project/.git/
SnapI now live in the hidden .git folder. You never need to touch it. Deleting it deletes all history!
Step 2 · Ask what's going on 
# create a file, then:
$ git status
On branch main
Untracked files:
    analysis.py
SamRed means Git sees the file but isn't tracking it yet. Got it.
Step 3 · Put it on stage 
$ git add analysis.py
$ git status
Changes to be committed:
    new file:   analysis.py

git add . stages everything changed in the folder. Handy, but check git status first.

Step 4 · Click! 
$ git commit -m "Add data loading script"
[main (root-commit) a1b2c3d] Add data loading script
 1 file changed, 12 insertions(+)
 create mode 100644 analysis.py

-m is the message. Write what this snapshot does. a1b2c3d is the commit's ID (a short “hash”); every commit gets a unique one.

The loop you'll repeat forever
edit files→ git status→ git add …→ git commit -m "…"↺
Chapter 5

Looking back & undoing

The photo album 
$ git log --oneline
e4f9a21 (HEAD -> main) Plot accuracy per epoch
b7c3d10 Fix off-by-one in data split
a1b2c3d Add data loading script
SnapNewest on top. HEAD is a “you are here” sticker on the snapshot you're currently on.
Spot the difference 
$ git diff
--- a/analysis.py
+++ b/analysis.py
-test_size = 0.3
+test_size = 0.2

git diff shows edits you haven't staged yet. git diff --staged shows what's about to be committed.

“Oops, I…” — quick fixes
Oops, I…
Do this
broke a file and want the last committed version back
git restore analysis.py
staged a file I didn't mean to
git restore --staged analysis.py
want to peek at an old version of a file
git show a1b2c3d:analysis.py
want to visit an old snapshot of the whole project
git switch --detach a1b2c3d … then git switch main to come back
made a typo in the last commit message (not pushed yet)
git commit --amend -m "Better message"
want to undo a commit that's already shared
git revert b7c3d10 (makes a new commit that cancels it)
Careful: git restore file throws away edits you never committed. Git can only bring back what it has a snapshot of.
Chapter 6

Branches: parallel universes

SamMy model works. Now I want to try a transformer, but I'm scared of breaking everything.
SnapMake a branch! It's a separate line of snapshots. main stays safe while you experiment.
$ git switch -c try-transformer   # create + move
# ...edit, add, commit as usual...
$ git switch main                 # back to safety
$ git merge try-transformer       # it worked? bring it in
$ git branch -d try-transformer   # tidy up
What it looks like inside Git

git branch lists your branches and marks the current one with *. Switching branches changes the files in your folder to match that branch, so commit (or stash) your work before switching.

Chapter 7

Merge conflicts (don't panic)

Both branches changed the same line
SnapI can't guess which one you want, so I ask you. That's all a conflict is.
Git marks the spot in the file 
<<<<<<< HEAD
lr = 0.001
=======
lr = 0.01
>>>>>>> try-transformer
  1. Open the file. Keep the version you want (or combine them).
  2. Delete the three marker lines.
  3. git add train.py
  4. git commit — done!

Want to bail out instead? git merge --abort puts everything back.

Chapter 8

Going online: GitHub & friends

SnapA remote is a copy of your repository on a server. push uploads your new snapshots, pull downloads new ones, clone copies a whole project to a new computer.
Option A · Project already online 
$ git clone https://github.com/ada/my-project.git
$ cd my-project

You get all files and the full history. The remote is already set up as origin.

Option B · You started locally 
# make an EMPTY repo on GitHub first, then:
$ git remote add origin git@github.com:ada/my-project.git
$ git push -u origin main   # first time
$ git push                  # every time after
Staying in sync 
$ git pull    # start of the day
# ...work, add, commit...
$ git push    # end of the day

Login tip: GitHub doesn't accept your password in the terminal. Set up an SSH key (search “GitHub SSH key”) or use a personal access token.

Chapter 9

.gitignore: what NOT to snapshot

SnapI'm the bouncer. Your code gets in. Big data, environments, and secrets stay outside.
Make a file called .gitignore 
# .gitignore — in the project root
.venv/
__pycache__/
*.pyc
.ipynb_checkpoints/
data/
*.csv
.env
.DS_Store

Each line is a pattern. Commit the .gitignore itself so teammates get it too.

Never commit passwords, tokens or API keys. Once pushed, assume they are public, even if you delete them later.
Chapter 10

Notebooks in Git

You changed one number…
SamI changed one learning rate and re-ran my notebook. Why does git diff show 900 changed lines?
What's really inside an .ipynb
SnapA notebook is a JSON text file. Besides your code, it stores every output, every plot as a huge block of encoded text, and the run number of each cell. Re-running changes all of them.
  "cell_type": "code",
- "execution_count": 3,
+ "execution_count": 7,
- "source": ["lr = 0.01"],
+ "source": ["lr = 0.001"],    ← your change
  "outputs": [{"data": {"image/png":
- "iVBORw0KGgoAAAANSUhEUgAA… (40 000 chars)"
+ "iVBORw0KGgoAAAANSUhEUgAB… (41 000 chars)"
Why that hurts
  1. Unreadable diffs. Your one real change drowns in output noise.
  2. Painful merges. Two people re-run the same notebook: conflicts inside JSON.
  3. A bloated repo. Every committed plot stays in the history forever.
  4. Leaks. Outputs can show data samples, file paths or tokens you never meant to publish.
Fix 1 · Clear outputs before you commit

In Jupyter: Edit → Clear Outputs of All Cells, save, then commit. Or from the terminal:

$ jupyter nbconvert --clear-output \
      --inplace analysis.ipynb
$ git add analysis.ipynb

Simple, but easy to forget. Fix 2 makes it automatic.

Fix 2 · Let Git do it: nbstripout 
$ pip install nbstripout
$ cd my-project
$ nbstripout --install
# from now on Git commits notebooks
# without outputs; your file keeps them

Run nbstripout --install once in each repository, on each computer you commit from.

Fix 3 · Readable notebook diffs: nbdime 
$ pip install nbdime
$ nbdime config-git --enable --global
$ git diff        # now cell by cell

nbdime shows what changed per cell (code, then outputs) instead of raw JSON, and also helps with merging notebooks.

Habits for notebooks in a repo
  1. Keep the real code in .py files. Notebooks import it and show results; plain Python diffs and merges cleanly. Issue #2 · Ch. 13
  2. One notebook, one person. Avoid editing the same notebook in parallel on two branches.
  3. Save the figures you need as files (plt.savefig("figures/loss.png")) instead of relying on notebook output.
  4. Ignore the clutter: .ipynb_checkpoints/ belongs in .gitignore (Chapter 9).
Chapter 11

Habits of Git pros

Snap's rules
  1. Commit small and often. One idea per commit. Several a day is normal.
  2. git status is your best friend. Run it before every add and commit.
  3. Pull before you start, push when you stop.
  4. Only commit code that runs on main. Experiments go on branches.
  5. Read the message Git prints. It usually tells you the next command.
Commit messages

Future you: “huh?”

  • stuff
  • asdfgh
  • changes
  • final fix (for real)

Future you: “ah!”

  • Add CSV loader for survey data
  • Fix train/test leakage in split
  • Tune learning rate to 1e-3
  • Remove unused plotting code

Start with a verb, like an instruction: “Add…”, “Fix…”, “Remove…”. Finish the sentence “This commit will…”.

SamSo I can try anything, and if it goes wrong I just go back?
SnapAs long as you committed first. Now go break things!
