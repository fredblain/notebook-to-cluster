Issue #3 · Shared GPU servers

Share
the GPU

Your laptop says training will take nine days. A shared GPU server can do it overnight, but you share it with everyone else on it. This issue covers getting in with SSH keys, running jobs with Slurm, watching them, and leaving the server as clean as you found it. The running example is GPU4EDU, a teaching cluster; the same ideas apply to any Slurm cluster.

Chapter 1

Meet the cluster

Part 1 · Get in
Thesis, week 6
SamMy laptop says one training run takes nine days. My deadline says no.
How the pieces fit

On GPU4EDU, the example in this issue, you log in to aurometalsaurus.uvt.nl with your u-number. That machine holds your files and the queue, but it has no GPU. To use a GPU you ask Slurm, the scheduler, which runs your work on a compute node when one is free.

SnapThink of a shared kitchen. The login node is the hallway: drop your bags, read the recipe. The GPUs are the stoves, and Slurm is the reservation list.
Two prompts in this issue 
~ ❯ ssh gpu4edu        # on your laptop
gpu4edu:~$ squeue --me   # on the cluster

A yellow prompt means “type this on your laptop”. A blue prompt means “type this on the cluster”. Mixing them up is the most common beginner mistake.

Chapter 2

SSH keys: why and how

Part 1 · Get in
Why bother?
SamWhy can't I just log in with a password, like everywhere else?
  1. Safer. A key is far too long to guess, unlike most passwords.
  2. Faster. No password every time you connect, copy a file or pull code.
  3. Needed for tools. rsync, scp, Git and scripts can connect without stopping to ask.
  4. Per device. One key per laptop. Lose a laptop, and only that key needs to be revoked.
A key comes in a pair

The public key is like a padlock you hand out: IT services install it on the server for you. Only your private key opens it, and that one never leaves your laptop.

Step 1 · Make the pair (laptop) 
~ ❯ ssh-keygen -t ed25519 -C "u123456 macbook"
Enter file in which to save the key
(/Users/sam/.ssh/id_ed25519): ⏎
Enter passphrase: ••••••••
Your public key has been saved in
/Users/sam/.ssh/id_ed25519.pub

Press Enter for the default location. A passphrase protects the key if your laptop is stolen. macOS can remember it in the Keychain, so you type it once. If the GPU4EDU instructions ask for a different key type, use that one.

Step 2 · Get the padlock installed

Some servers let you install your key yourself with ssh-copy-id. On GPU4EDU you can't: IT services do that, after you share your public key with them through SURF.

~ ❯ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… u123456 macbook
~ ❯ pbcopy < ~/.ssh/id_ed25519.pub   # macOS: copy it
  1. Copy the whole line, from ssh-ed25519 to the comment at the end.
  2. Share it via SURF, following the GPU4EDU SSH instructions (GPU4EDU page → Tutorial → Account).
  3. Wait until your key has been installed, then continue with step 3.
Pasted text starts with -----BEGIN OPENSSH PRIVATE KEY-----? Stop: that's your private key. Share only the .pub file.
Step 3 · A nickname for the server 
# ~/.ssh/config  (on your laptop)
Host gpu4edu
    HostName aurometalsaurus.uvt.nl
    User u123456
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60
    AddKeysToAgent yes
    UseKeychain yes      ← macOS only
~ ❯ ssh gpu4edu
gpu4edu:~$ ✓ no password!
~ ❯ scp notes.md gpu4edu:~/thesis/

gpu4edu now works everywhere: ssh, scp, rsync. ServerAliveInterval keeps a quiet connection from timing out. Remove the UseKeychain line on Linux or WSL.

Key safety
  1. Never send, upload or share id_ed25519 (the file without .pub). Not even with a TA.
  2. Lost a laptop, or think a key leaked? Tell IT services so that key is revoked, then make a new pair and share the new public key.
  3. One key per device. Name each one in the comment (-C "u123456 macbook") so you and IT services know which key is which.
  4. Never share your account either. Everything that runs under your u-number is your responsibility.
Chapter 3

One codebase, two machines

Part 1 · Get in
SnapGolden rule: write code on your laptop, run it on the cluster. Git carries the code between them, so both always have the same version.
The daily loop 
# laptop: change code, then
~ ❯ git commit -am "Add dropout"
~ ❯ git push
# cluster: get it, then run
gpu4edu:~/thesis$ git pull
gpu4edu:~/thesis$ make run EXP=baseline

Always git pull before you submit, or you'll run yesterday's code. Git Good · Ch. 8

First time on the cluster 
# private repo: give the cluster its own key
gpu4edu:~$ ssh-keygen -t ed25519 -C "u123456 gpu4edu"
gpu4edu:~$ cat ~/.ssh/id_ed25519.pub
# paste into GitHub → Settings → SSH keys
gpu4edu:~$ git clone git@github.com:sam/thesis.git

The same idea as Chapter 2, one level up: now the cluster proves who it is to GitHub. A public repo can simply be cloned over HTTPS.

What travels how
ThingHow
Code, configs, Makefile, job scriptsGit
Datasetsrsync, once
Logs, results, checkpointsrsync back; never in Git
rsync: copy only what changed 
# data to the cluster (once)
~/thesis ❯ rsync -avz --progress data/ gpu4edu:~/thesis/data/
# results back home
~/thesis ❯ rsync -avz gpu4edu:~/thesis/runs/ runs/

Mind the trailing / on folders: data/ copies the folder's contents. Add data/ and runs/ to .gitignore. Git Good · Ch. 9

Quick fix on the cluster?
SnapIt happens. Then commit and push it from the cluster right away, and git pull on your laptop. Two machines editing the same file without syncing = merge conflict. Git Good · Ch. 7
Chapter 4

Slurm: take a number

Part 2 · Run
SnapYou don't grab a GPU. You ask Slurm for one, like taking a number at the bakery. When a GPU is free, Slurm runs your job on it.
Two ways to ask
srunsbatch
WhatRuns a command right now and shows the output in your terminalQueues a script; returns your prompt immediately
If your connection dropsThe job dies with itKeeps running
Use forQuick checks (seconds to minutes), a short interactive lookEverything else: training, evaluation, anything you'd leave running
 
# quick check: does a GPU node see the GPU?
gpu4edu:~$ srun -p GPU --gres=gpu:1 --time=00:05:00 nvidia-smi
# short interactive session on a GPU node
gpu4edu:~$ srun -p GPU --gres=gpu:1 --time=00:30:00 --pty bash -l
# … test things …  then ALWAYS:
exit
An open interactive session keeps a GPU reserved, even while you're at lunch. Type exit the moment you're done.
A job script, line by line 
#!/bin/bash
#SBATCH --job-name=baseline
#SBATCH --partition=GPU
#SBATCH --nodes=1
#SBATCH --gres=gpu:1
#SBATCH --cpus-per-task=4
#SBATCH --mem=16G
#SBATCH --time=02:00:00
#SBATCH --output=logs/%x-%j.out
#SBATCH --error=logs/%x-%j.err

set -e
. /usr/local/anaconda3/etc/profile.d/conda.sh
conda activate thesis

echo "Started on $(hostname) at $(date)"
python train.py --config configs/baseline.yaml
echo "Finished at $(date)"
  1. 1#SBATCH lines are not comments. Slurm reads them as the job's settings: a name, the GPU partition, one GPU (--gres=gpu:1), CPUs and memory.
  2. 2--time is a hard limit. Slurm stops the job when it runs out. Ask for a realistic upper bound, not “3 days just in case”: a modest request is fairer to others and is often scheduled sooner.
  3. 3%x and %j become the job name and job ID. The logs/ folder must exist before you submit (mkdir -p logs).
  4. 4Activate conda inside the script. A batch job starts a fresh shell that doesn't know conda activate until you load conda.sh. Issue #2 · Ch. 6
  5. 5Echo the start and end time. sacct (Slurm's job history) is switched off on GPU4EDU, so these two lines are your record of how long a run took.
gpu4edu:~/thesis$ mkdir -p logs
gpu4edu:~/thesis$ sbatch job.sh
Submitted batch job 123456
gpu4edu:~/thesis$ sinfo -p GPU         # are nodes idle, mixed or fully allocated?
Chapter 5

Many runs: job arrays

Part 2 · Run
Five seeds, five scripts?
SamMy supervisor wants the same model trained with five random seeds. Do I copy job.sh five times and submit each one?
SnapNo: one script, one sbatch, five tickets. Slurm calls that a job array.
One job, numbered tasks

Every task runs the same script, with its own number: $SLURM_ARRAY_TASK_ID. Your script uses that number to pick a seed, a config or a data file.

Good for
  1. Repeats: the same run with several seeds.
  2. Small sweeps: a handful of configs or learning rates.
  3. Many inputs: one data file, language pair or fold per task.

The tasks must be independent: no task may need another task's output.

Step 1 · The array script, line by line 
#!/bin/bash
#SBATCH --job-name=seeds
#SBATCH --partition=GPU
#SBATCH --gres=gpu:1
#SBATCH --cpus-per-task=4
#SBATCH --mem=16G
#SBATCH --time=02:00:00
#SBATCH --array=0-4%2                 1
#SBATCH --output=logs/%x-%A_%a.out    2
#SBATCH --error=logs/%x-%A_%a.err

set -e
. /usr/local/anaconda3/etc/profile.d/conda.sh
conda activate thesis

SEED=$SLURM_ARRAY_TASK_ID             3
OUT=results/seed-$SEED                4
mkdir -p "$OUT"

echo "Task $SEED started on $(hostname) at $(date)"
python train.py --config configs/baseline.yaml \
                --seed "$SEED" --out "$OUT"
echo "Finished at $(date)"
  1. 1--array=0-4 creates five tasks, numbered 0 to 4. %2 lets at most two of them run at the same time; the others wait their turn.
  2. 2%A becomes the array's job ID and %a the task number, so each task writes its own log: seeds-123460_3.out. With plain %j, you couldn't tell which log belongs to which seed.
  3. 3$SLURM_ARRAY_TASK_ID is the only thing that differs between tasks. Here it becomes the seed.
  4. 4One output folder per task. Five tasks that all save to model.pt overwrite each other, and you keep whichever finished last.
--gres=gpu:1 is per task. Without the %2, --array=0-4 can take five GPUs at once. On a shared server, that may be all of them.
gpu4edu:~/thesis$ mkdir -p logs
gpu4edu:~/thesis$ sbatch array.sh
Submitted batch job 123460
Step 2 · Choosing the numbers
--array=Task numbersTypical use
0-40, 1, 2, 3, 4Five seeds
1,3,71, 3, 7Re-run only the tasks that failed
0-20:50, 5, 10, 15, 20Steps of 5 (for example a range of sizes)
0-9%30 to 9, at most 3 running at a timeAny array on a shared server

An option given to sbatch on the command line overrides the #SBATCH line, so sbatch --array=1,3 array.sh re-runs just tasks 1 and 3 without editing the script.

Step 3 · Different configs 
#SBATCH --array=0-2%2

CONFIGS=(baseline lr-small lr-large)
EXP=${CONFIGS[$SLURM_ARRAY_TASK_ID]}

python train.py \
  --config "configs/$EXP.yaml" \
  --out "results/$EXP"

A bash list starts counting at 0, like the task numbers. Three configs means --array=0-2: keep the two in step when you add one.

Step 4 · Watch and cancel 
gpu4edu:~$ squeue --me
       JOBID PARTITION  NAME     USER ST  TIME NODES NODELIST(REASON)
123460_[2-4]       GPU seeds u123456 PD  0:00     1 (JobArrayTaskLimit)
    123460_0       GPU seeds u123456  R  3:12     1 cerulean
    123460_1       GPU seeds u123456  R  3:12     1 cerulean
Command
Does
squeue --me -r
One line per task, also for waiting tasks.
scancel 123460_3
Cancels task 3 only.
scancel "123460_[2-4]"
Cancels tasks 2 to 4. Keep the quotes: zsh otherwise reads the brackets as a file pattern and stops with no matches found.
scancel 123460
Cancels the whole array: running and waiting tasks.

(JobArrayTaskLimit) means the tasks are waiting because of your own %2, not because the server is full.

Logs per task 
gpu4edu:~/thesis$ ls logs/
seeds-123460_0.err
seeds-123460_0.out
seeds-123460_1.err
seeds-123460_1.out  # …and so on
gpu4edu:~/thesis$ grep -il error logs/*.err
logs/seeds-123460_1.err

One failed task doesn't stop the others. Find it, fix it, then resubmit only that one: sbatch --array=1 array.sh.

Do

  • Test one task first: sbatch --array=0 array.sh, with a short --time.
  • Always set a % limit. Two is a polite default on a small shared server.
  • Give every task its own output folder and its own log (%A_%a).
  • Cancel the whole array as soon as you spot a bug in task 0. The other tasks have the same bug.

Don't

  • Submit a 200-run grid search to a teaching server. Pick the few settings that matter.
  • Use an array for a chain (prepare data → train → evaluate). Tasks run in any order.
  • Use tiny tasks of a few seconds. Each task waits in the queue and loads your model again; loop inside one job instead.
  • Use an array to get round a per-user limit. It is still your jobs, and admins see it that way.

Servers set their own limits on array size and on how many jobs one person may run. On GPU4EDU, as for every rule in this issue, the server's own documentation comes first.

Chapter 6

Stay connected: screen

Part 2 · Run
The problem
SamI closed my laptop on the train and my tail -f and my srun session were just… gone.
The fix
Snapscreen keeps a terminal running on the server. You can detach, disconnect, reconnect tomorrow from another laptop and pick up exactly where you left off.
gpu4edu:~$ screen -S thesis      # start a named session
# … work …   Ctrl+a d to detach
gpu4edu:~$ screen -ls            # list sessions
gpu4edu:~$ screen -r thesis      # reattach
Split the screen
Keys
Does
Ctrl+a S
split top / bottom
Ctrl+a |
split left / right
Ctrl+a Tab
move to the next region
Ctrl+a c
start a shell in it (new regions start empty!)
Ctrl+a d

Good to know
  1. sbatch jobs don't need screen to survive a disconnect. Screen is for your windows: monitoring, an interactive srun, editing.
  2. tmux does the same job and is common on other servers. It isn't installed on GPU4EDU, so this issue uses screen.
  3. Close sessions you're done with: screen -X -S thesis quit. Detached sessions live forever otherwise.
Chapter 7

Organise runs with a Makefile

Part 2 · Run
Three weeks later…
SamWhich config gave me 81.6? Was it out2.log? Or model_final_new.pt?
One folder per run 
thesis/
├── Makefile
├── job.sh
├── train.py
├── configs/
│   ├── baseline.yaml
│   └── lr-small.yaml
└── runs/                       ← in .gitignore
    └── 20261014-1530_baseline/
        ├── config.yaml         ← exact copy of the settings used
        ├── commit.txt          ← which version of the code
        ├── logs/               ← Slurm .out and .err
        └── results.json, model.pt

Every number you report can now be traced to its settings, its code version and its log. The Makefile below builds this for you, the same way every time.

The Makefile 
# Makefile
EXP ?= baseline
RUN := runs/$(shell date +%Y%m%d-%H%M)_$(EXP)

.PHONY: run status clean

run:            ## new run folder + submit
	@git diff --quiet || (echo "Commit first!"; exit 1)
	mkdir -p $(RUN)/logs
	cp configs/$(EXP).yaml $(RUN)/config.yaml
	git rev-parse --short HEAD > $(RUN)/commit.txt
	sbatch --job-name=$(EXP) \
	  --output=$(RUN)/logs/%x-%j.out \
	  --error=$(RUN)/logs/%x-%j.err \
	  job.sh $(RUN)

status:
	squeue --me

clean:          ## remove Python caches
	find . -name __pycache__ -type d -prune -exec rm -rf {} +
# job.sh: last lines now use the run folder
RUN_DIR="$1"
python train.py --config "$RUN_DIR/config.yaml" \
                --out "$RUN_DIR"
gpu4edu:~/thesis$ make run EXP=lr-small
Submitted batch job 123457
gpu4edu:~/thesis$ make status
gpu4edu:~/thesis$ make -n run   # dry run: print, don't do
  1. 1EXP ?= baseline is a default you override on the command line.
  2. 2The first line refuses to run with uncommitted changes, so commit.txt always tells the truth.
  3. 3--output on the command line overrides the #SBATCH line in job.sh.
Recipe lines must start with a real Tab, not spaces. Otherwise: *** missing separator. Stop. In vim, :set list shows tabs as ^I.

Chapter 9

nvidia-smi: is my GPU actually working?

Part 3 · Watch
Ask from inside your job
SnapThe login node has no GPU, so nvidia-smi there tells you nothing. Step into your running job and ask there.
# one snapshot
gpu4edu:~$ srun --jobid=123456 --overlap nvidia-smi
# a line every 5 s: power, utilisation
gpu4edu:~$ srun --jobid=123456 --overlap \
      nvidia-smi dmon -s pu -d 5

--overlap lets this small command share your job's resources instead of asking for new ones.

Reading the table 
+-----------------------------------------------------------------------------+
| GPU  Name        Temp   Pwr:Usage/Cap |        Memory-Usage  | GPU-Util     |
|=======================================+======================+==============|
|   0  NVIDIA A40   61C  3212W / 300W | 231240MiB / 46068MiB| 197%      |
+-----------------------------------------------------------------------------+
| Processes:   PID   Type   Process name                       GPU Memory    |
|4          48213    C    python                               31200MiB    |
+-----------------------------------------------------------------------------+
  1. 1GPU-Util: how busy the GPU is. Training should be high most of the time.
  2. 2Memory: how much of the A40's 48 GB your model and batches take.
  3. 3Power: what it draws right now. Busy GPUs draw far more than idle ones (Chapter 11 turns this into CO₂).
  4. 4Processes: your program, and how much memory it holds.
What the numbers tell you
You seeIt probably meansTry
Util 80–100%, memory well usedAll good: the GPU is earning its keepNothing. Go have a coffee
Util jumps between 0% and 100%The GPU waits for data between batchesMore data-loader workers (num_workers), data on local disk, bigger batches
Util 0%, no python process listedYour code runs on the CPU: a GPU reserved for nothingCheck torch.cuda.is_available() and that you move the model and data .to("cuda"); scancel and fix
Memory almost fullClose to CUDA out of memorySmaller batch size or shorter sequences Issue #2 · Ch. 10
Memory almost empty, util lowThe job is small for this GPUBigger batches; or is a GPU needed at all?
 
In [1]: import torch
        print(torch.cuda.is_available(), torch.cuda.get_device_name(0))
Out[1]: True NVIDIA A40

Put that line at the top of your training script. If the log says False, stop the job: it isn't using the GPU it holds.

Part 3 · Watch

ST / Reason
Means
R
Running.
PD (Resources)
Pending: waiting for a GPU to become free.
PD (Priority)
Pending: other jobs are ahead of you in line.
CG
Completing: wrapping up.

Finished, failed or cancelled. Read the log to find out which.
Stop a job 
gpu4edu:~$ scancel 123457
SnapSaw a bug in the log? Wrong config? Cancel right away. A job you no longer need is a GPU someone else is waiting for.

scancel --me cancels all your jobs. Use with care.

Snapshot vs stream: pick the right tool 
gpu4edu:~$ watch -n 10 squeue --me

watch reruns a command every few seconds and redraws the screen. Right for a snapshot that changes, like the queue, where jobs appear and disappear.

gpu4edu:~$ tail -f runs/…_baseline/logs/baseline-123456.out

tail -f follows new lines as they're added to a file. Right for a stream that grows, like a log.

Ctrl+C stops watching. It does not stop the job. Put both in a screen session with two regions and you have a control room that survives a closed laptop.

After the job 
gpu4edu:~$ grep -i error logs/*.err
gpu4edu:~$ head -1 logs/baseline-123456.out
Started on cerulean at Tue 14 Oct 15:30
gpu4edu:~$ tail -1 logs/baseline-123456.out
Finished at Tue 14 Oct 17:12

On clusters with job accounting, sacct gives elapsed times. On GPU4EDU it is switched off, so your own timestamps are the record.

Chapter 11

Bonus: what did that cost the planet?

Part 3 · Watch · optional
Optional, but worth it
SnapEvery job draws electricity, and the grid isn't carbon-free. Usually nobody tells you how much. CarbonTracker does.
  1. Awareness: more papers include a short carbon statement next to their results.
  2. Reporting: universities and funders increasingly ask for it.
  3. Optimising: a measured number shows whether the smaller model or shorter run really saved energy.
Add four lines to your training loop 
train.py
from carbontracker.tracker import CarbonTracker

tracker = CarbonTracker(epochs=EPOCHS, components="gpu",
                        log_dir="carbontracker_logs/")
for epoch in range(EPOCHS):
    tracker.epoch_start()
    train_one_epoch(model, loader)
    tracker.epoch_end()
tracker.stop()

Install it once in your environment: pip install carbontracker. components="gpu" because measuring the CPU needs administrator rights (Intel RAPL) that students don't have on GPU4EDU. The report therefore covers the GPU only.

The report (in carbontracker_logs/) 
Actual consumption for 50 epoch(s):
        Time:   1:41:52
        Energy: 0.35 kWh
        CO2eq:  … g
        This is equivalent to:
        … km travelled by car
CarbonTracker: Average carbon intensity during training was
… gCO2/kWh at detected location: Tilburg, North Brabant, NL.

Same energy, different grid, different CO₂: the result depends on how clean the electricity is at that moment, not only on how much you used. (Numbers above are illustrative; yours come from your own run.)

Cross-check it

A number that matters deserves a second opinion. While the job runs, the power column of nvidia-smi dmon should rise well above idle:

gpu4edu:~$ srun --jobid=123456 --overlap \
  nvidia-smi dmon -i 0 -s mpucv -d 1 -o TD

No time to instrument? The ML CO₂ Impact calculator (mlco2.github.io/impact) gives a rough estimate from GPU type and hours.

gpu4edu:~$ conda env list                  # environments you no longer use?
gpu4edu:~$ conda env remove --name old-env
Project hygiene
  1. Delete checkpoints of failed and test runs. Keep the best one, not every epoch.
  2. One copy of each dataset, not one per experiment folder.
  3. The cluster is not a backup. Copy results home with rsync (Chapter 3) and keep code on GitHub.
  4. Finished the course or thesis? Copy what you need, then delete the rest.
Chapter 13

House rules

Part 4 · Be a good neighbour
SnapA shared server is set up for a specific group and purpose: GPU4EDU, for example, is for students in the courses that use it. Everyone shares the same few GPUs, often in the same deadline week. These habits keep it fair.

Do

  • Test small first. A tiny run with a short --time before the big one. Issue #2 · Ch. 8
  • Ask for what you need. One GPU unless your code really uses more; a realistic time limit.
  • Use sbatch for anything longer than a quick check.
  • Watch your first minutes. Is the GPU busy? Is the loss going down?
  • Cancel what you don't need, as soon as you know.
  • Plan for deadlines. The queue is longest the week before submission. Start early.
  • Ask for help in your server's support channel (for GPU4EDU, its Google Chat): include the job ID, your script and the error.

Don't

  • Train on the login node. It has no GPU and everyone shares it.
  • Leave an interactive GPU session idle, overnight or over lunch.
  • Submit ten copies to see which one starts first.
  • Share your account or private key, or use someone else's.
  • Copy data you aren't allowed to: check your data agreement and ethics approval before uploading personal or sensitive data.
  • Use it for things it isn't meant for: on a teaching server like GPU4EDU that means coursework only; no personal projects, mining or gaming.
  • Try to work around limits or look into other people's files.

This page describes good practice. Your course's rules and your server's official documentation (for GPU4EDU: ilk.uvt.nl/~shterion/gpu4edu.html) always come first.
